# Habitat/dispersal determinism hygiene composition

**Cited:** [vegetation/habitat review](../reviews/2026-07-31-vegetation-habitat-review.md) §2.4; T-001 Locked; T-005; §2.1 Symmetry invariant class.

## Three defects, one region of code

`habitatProcess`'s declared `reads` omitted `this.terrain.data` (feeds `terrainInsolation`) and `this.soilMaterial.data` (feeds `substrateProps(...).porosity`) — both silently consumed inside `runHabitatStep`, invisible to any future scheduler dependency analysis (T-005: registered fields inspectable means the declaration has to be honest, not just the field). `runHerbEstablishmentStep` updated the six guilds sequentially, and downstream guilds read biomass arrays upstream guilds in the *same tick* had already overwritten (shrub read `herbBiomass[i]` after herb's own update; crust read all five other guilds' post-update biomass) — a Gauss-Seidel step where §2.1's Symmetry invariant class calls for order-independence. And `runDispersalStep` (annual band) and `runHerbEstablishmentStep` (seasonal band) computed the *identical* six-guild HSI math from the same `evaluateXHsi` functions at different cadences, so the seed-pressure-driven `veg.establishment.*` field the annual pass wrote could silently disagree with the HSI that actually drove seasonal growth.

## One fix closes both the duplication and the ordering gap

The Gauss-Seidel bug and the duplicate-math bug turned out to be the same code doing two things at once. Fixing the second (source guild HSI from wherever it's actually authoritative, instead of recomputing it) removes the first as a structural consequence: once `runHerbEstablishmentStep` no longer calls `evaluateStrandHsi` / `evaluateBinderHsi` / `evaluateMarshHsi` / `evaluateShrubHsi` / `evaluateCrustHsi` itself, there is no live cross-guild biomass read left inside its loop to be order-dependent about.

Five new registered fields carry the annual-band HSI forward: `habitat.strandSuitability`, `habitat.binderSuitability`, `habitat.marshSuitability`, `habitat.shrubSuitability`, `habitat.crustSuitability` (herb already had this — `habitat.suitability`, written daily by `habitatProcess`, independent of dispersal). `runDispersalStep`'s `writeCell` writes each guild's `evaluateXHsi(...).hsi` into its field in the same pass it already computes establishment probability from that HSI, so the two can no longer drift apart. `dispersalProcess.writes` and `vegetationSeasonalProcess.reads` were updated to match; `vegetationSeasonalProcess.reads` also dropped `shore.exposure` / `soil.salinity` / `soil.moisture` / `soil.material` / `shore.longshore` / `terrain.elevation` — none of those raw fields are read in that process any more.

`runHerbEstablishmentStep` itself collapsed from ~170 lines of six near-identical blocks to a data-driven loop over a `GuildEstablishmentInputs[]` (`arrivalComposition.applyGuildEstablishment`, exported so it's unit-testable without a `WorldState`). Each entry reads only its own pre-call biomass, seed bank, and suitability — fields an earlier band already committed — and writes only its own biomass array. No entry's result depends on another entry's output within the call, which is the Jacobi property the review asked for: the six guilds can be evaluated in any order and each produces a byte-identical result.

## Why this doesn't delay founding

`WorldState`'s constructor already runs one `runDispersalStep(1)` at construction ("fixed perimeter seed pressure available from t=0" — pre-existing, `WorldState.ts` constructor tail), so the new suitability fields are populated from t=0 exactly like seed banks always were; a fresh world's first seasonal establishment tick has real, non-zero guild suitability to read, not a zeroed field waiting on the first annual band commit (day 36 at default rates). Non-herb guild founding timing is unchanged by this slice.

## Test fallout this surfaced, and the fix in each case

Several existing tests and probes (`shrubArrival.test.ts`, `crustArrival.test.ts`, `probeShrubArrival`, `probeCrustArrival`) constructed a `WorldState`, then set up scenario-specific conditions (air temperature, herb biomass fraction, moisture) *after* construction, then called `runHerbEstablishmentStep` directly in a loop without ever calling `runDispersalStep` again. Pre-fix, this worked because `runHerbEstablishmentStep` recomputed guild HSI itself every tick from whatever the fields held *right then* — the exact Gauss-Seidel-adjacent behavior this slice removes. Post-fix, those tests' guild suitability stayed frozen at the constructor's initial (pre-setup, default-condition) dispersal pass, understating or zeroing the scenario's intended signal. The fix in each case is a one-line `world.runDispersalStep(1)` added after the scenario's real conditions are set and before the establishment loop — the same pattern `probeStrandArrival`, `probeBinderArrival`, `probeSalinityArrival`, `probeHeatArrival`, `probeSprayArrival`, `probeArrivalEarned`, `probeLivingHollow`, and `probeIslandArrival` already used. Guild seed banks are still overridden with controlled uniform fills immediately after, exactly as before — only the suitability field's source changed.

## Baselines moved, and why

`deep-time`, `regime-divergence`, `branch-compare`, `burn-recover`, `island-drainage`, `tidal-envelope`, `shore-exposure`, `longshore-drift`, `orographic-wind`, `salinity-arrival`, `heat-arrival`, `strand-arrival`, `binder-arrival`, `marsh-arrival`, `spray-arrival`, `inundation-arrival`, `light-arrival`, `island-arrival`, `substrate-contrast`, `substrate-deposit`, `hillslope-deposit`, `cloud-delivery`, `event-band-gate`, `season-regime`, `erosion-intensity` moved on `hashN` only (the full-registry `stateHash()` folds every registered field's id and data into the hash; five new fields necessarily change it for every scenario that reports a hash, whether or not that scenario's own physics touch vegetation) — mechanical, not a signal of a computational change in those scenarios' own domain.

`disturbance-recovery`, `living-hollow`, `shrub-arrival`, and `crust-arrival` also moved on real (non-hash) metrics — the direct, intended consequence of guild growth no longer riding a same-tick recompute of a co-guild's just-updated biomass. `shrub-arrival`'s `warmCovered.shrubBiomass` (1.92 → 1.76) is the clearest case: pre-fix, shrub's HSI recomputed every seasonal tick against herb biomass that was *itself* growing across the same 8-tick loop, so shrub's suitability crept upward tick over tick; post-fix it's frozen at the single `runDispersalStep` snapshot taken once, before the loop. Every hard threshold the probe and its unit-test twin assert (`> 0.1`, climate delta `> 0.05`, cold/mild/bare `=== 0`) still holds — only the exact magnitude moved. `deep-time`'s `y*.meanCover` and `p005.hashFirstN`/`hashSecondN` moved for the same reason over a longer horizon; conservation (`massResidual`) stayed within its existing bound throughout.

## Tests

- `src/sim/arrival.test.ts`: `applyGuildEstablishment` order-independence — six distinct guild specs run forward and reversed produce byte-identical per-guild biomass (closes the Symmetry gap directly); a second test confirms perturbing one guild's inputs never moves another guild's result. A third integration test (`establishment step doesn't recompute guild suitability`) mutates the raw environmental fields the old recompute would have read live, between an initial `runDispersalStep` and a `runHerbEstablishmentStep` call, and asserts `binderSuitability` is unchanged — the direct regression test for the duplicate-math fix.
- `src/sim/ownership.test.ts`: `habitatProcess.reads` contains `terrain.elevation` and `soil.material`; `dispersalProcess.writes` / `vegetationSeasonalProcess.reads` both name all five new suitability fields.
- `src/sim/shrubArrival.test.ts`, `src/sim/crustArrival.test.ts`: updated to call `runDispersalStep` after scenario setup (see above); assertions unchanged.

## Deferred

- §2.5's two minor findings from the same review (no cast-shadow term in `terrainInsolation`; `veg.cover` decay is a linear decrement rather than proportional to standing stock) are untouched — the review marked them "Minor" and outside this slice's three named defects.
- `veg.biomass.strand` / `.binder` / `.marsh` / `.shrub` / `.crust` remain undeclared as `reads` on `vegetationSeasonalProcess` despite being read (their own prior-tick value) and written every call — the same gap `veg.biomass.herb` alone was already exempt from before this slice. Not named by the review's three findings; left as found rather than expanding scope.
